CONFIRMED WRITE PATH (foundation for everything below)
--------------------------------------------------------------------------------
cs-digital-mfg `clerk_load.process_county` runs per county. For each clerk
record it classifies insert-vs-update by matching tblRecord on
(StateID, CountyID, normalized recordNumber, fileDate), county derived from the
scraper feed's diml_county_name -> tblLookupCounties.DIMLCountyName -> CountyID.
  - new_record_query.sql:1-19  -> NEW rows get record_id = newid() (fresh GUID).
  - existing_record_query.sql:20-21 -> UPDATE reuses tr.recordID, statusID=10 only.
  - package_id / document_dataset_id are NOT in the match key; both come from the
    scraper feed per record. original_file_name = "{'package_id','dataset_id'}"
    (clerk_load.py:181-184).
  - County is never derived from the document: headers["county_id"]=county.CountyID
    (clerk_load.py:177).
  - TblDimlXRef.insert is a blind INSERT...FROM SELECT, no existence check, no
    unique constraint on recordID (models.py:113-121).

Consequence: same document re-tagged under a different county (LND-6879 scraper
instability) misses the county-scoped match -> classified NEW -> fresh recordID +
new xref row carrying the SAME package_id. One package_id, many recordIDs, many
counties.

RESOLVED GATES (from prior code review)
  §9  IIE TRUSTS the supplied countyName; no document-based county detection
      (single_chunk_iie_processor.py:97-102, 345-414).
  §10 OCR RE-PULLS the PDF from DIML by package_id; imageLocation is a fallback
      used only when DIML has no instrument_pdf root (single_chunk_ocr_processor.py:166-182).

ITEM 1 — TRUE-COUNTY SOURCE OF TRUTH FOR THE 2,192 (cross-county)
================================================================================
STATUS: external dependency — the only item we cannot fully drive ourselves.

Finding:
  Nothing inside CS_Digital is independent of the bad county signal. County comes
  from the scraper (diml_county_name); the DIML package was created by the same
  scraper with the same bad county; IIE trusts whatever county we pass (§9). So
  there is no in-house authoritative county already stored.

Solution:
  Authoritative source = the CORRECTED OKCR scraper feed (LND-6879). For each
  affected instrument, re-derive county by joining the corrected source on
  (instrument_number, file_date) and write it into the fixed-dataset CSV's
  countyName column.

  Confirm with the LND-6879 owner:
    (a) Does the fix RE-TAG / BACKFILL existing OK records, or only correct new
        ones? If it backfills, re-measure first — much of the 2,192 may
        self-resolve. If not, we pull corrected county per instrument ourselves.
    (b) Can we query the corrected OKCR source by (instrument_number, file_date)
        to obtain the true county?

  In-house fallback (if the scraper cannot supply it):
    OK deeds carry "STATE OF OKLAHOMA, COUNTY OF ___" in the header. COLE OCRs
    the document anyway, so a one-off pass over the combined_ocr_result text with
    a `COUNTY OF (\w+)` extraction yields a per-record true county independent of
    the scraper. Small script, not a pipeline change.

Owner / decision: LND-6879 owner (backfill + source query); fallback is ours.

ITEM 2 — CORRECT-DOCUMENT DETERMINATION FOR THE 668 (different-PDF)
================================================================================
STATUS: solvable in-house.

Finding:
  The 668 is a PROXY — LND-6796.sql:51-67 counts distinct originalFileName
  (= distinct document_dataset_id) under one package_id; the SQL itself flags it
  as unconfirmed (not proven byte-different PDFs). Each record's OWN image
  (tblS3Image.s3FilePath / tblRecord.storageFilePath) IS the document the scraper
  bound to that record — images.py physically wrote one copy per record at
  creation. So "the correct document for record R" already exists: R's own
  imageLocation.

Solution:
  Extend the existing LND-8451_diml_pdf_check.py (built for Shape 2 pairs) to the
  Shape 1 668: compare the root instrument_pdf download_url across the datasets in
  each package.
    - Same PDF  -> registration artifact, nothing to fix.
    - Different -> the record's own imageLocation is the authoritative per-record
                   document (better than the package's "latest root," which is
                   what COLE would otherwise grab).
  Either verdict resolves to "use each record's own image" -> flows into Item 3.

Owner / decision: ours. No external dependency.

ITEM 3 — package_id-SPLITTING MECHANISM
================================================================================
STATUS: solvable in-house — biggest unlock; folds in Item 2 and the §10 artifact
        problem.

Finding:
  Do NOT manually split DIML packages. The code gives a cleaner path:
    - COLE package_enricher looks up package_id from tblDimlXref by recordID
      (package_enricher.py:60-92). If it finds NONE, it mints a fresh per-record
      package and inserts the new mapping.
    - OCR _download_pdf (single_chunk_ocr_processor.py:166-182) finds no
      instrument_pdf root on a brand-new package and falls back to the supplied
      imageLocation — i.e. OCRs the record's OWN image.

Solution:
  DELETE the shared tblDimlXref rows for the affected records BEFORE the COLE
  fixed-dataset run. COLE then:
    - mints one package per record,
    - OCRs each record's own correct PDF,
    - writes PER-RECORD artifacts.
  This simultaneously fixes the different-PDF problem (Item 2) AND the
  last-writer-wins shared-artifact problem (§10), in one move. No DIML surgery.

  Required ordering: delete affected xref rows -> (county corrected per Item 1,
  imageLocation already correct) -> upload fixed dataset -> COLE recompute.

Caveats (confirm with COLE owner before running at scale):
    - Deleting xref rows orphans the old shared packages' artifacts (harmless/stale).
    - Transient window where the producer sees no binding until COLE repopulates.
    - Strongly supported by the code; validate with the COLE owner.

Owner / decision: COLE owner sign-off on delete-then-recompute; execution is ours.
