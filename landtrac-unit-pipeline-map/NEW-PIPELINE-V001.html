NEW-PIPELINE-V001 — Target Landtrac Unit Pipeline

DIV1 removed on both sides. Well enrichment re-sourced from enverus.data.foundations_wells (Databricks Unity Catalog) keyed on UWI 12/14; daapUnitID minted by a new Hendrix sequence instead of the prodloader05 round-trip; message identity moves to UWI on a new v4 topic that runs in parallel with v3 until consumers migrate. Green = new/changed; every decision below shows the recommended value and the team options. Presentation draft — nothing built until ratified.

One-sentence summary. DIV1 disappears on both sides — the producer's well enrichment comes from foundations_wells in Unity Catalog keyed on UWI, and daapUnitID is minted by a new Hendrix sequence instead of the prodloader05/Shapeloader round-trip; the message identity moves to UWI on a new v4 topic that runs alongside v3 until consumers migrate.

Target design — decision by decision

D4 · PRE-WORKWell enrichment source — foundations_wells on UWI
✅ Recommended. Producer + point-feed read enverus.data.foundations_wells, keyed on api_uwi_12 with dedup/roll-up to one row per well. This one table carries the resolved strings the producer rebuilds via 5 DIV1 lookup joins, so it retires 6 of the 8 DIV1 tables outright (tblWell + State/County/Abstract/WellStatus/Company). Only tblDaapUnit (→ Hendrix seq) and tblDaapUnitDocumentMapping remain.
  • ⇄ Key on api_uwi_14 — clean ~1:1, no dedup, but 13.8% NULL uwi_14 drops ~14% of wells. Viable only if those wells are confirmed out-of-scope. option
  • ⇄ Mirror the 8 DIV1 tables into UC — column-for-column repoint, preserves WellID/daapUnitID identity, voids the UWI pivot + D5a. Lower design risk, keeps a DIV1-shaped schema alive. option
  • ⚠ Gating pre-work. GIS service principal needs UC read grants; then coverage-join % vs DIV1, attribute-vocab parity (envwellstatus strings vs DIV1 codes), and confirm unit↔well match length (pipeline historically used API-10).
D1 · TEAMWhere daapUnitID is minted — new Hendrix sequence
✅ Recommended: Hendrix-authoritative with UC ingest. A new Hendrix sequence/table mints daapUnitID when a QC'd polygon lands in UNIT_POLYGON. Hendrix = write-side system of record; UC ingests off it. The sequence must be seeded from DIV1 tblDaapUnit, next-value = MAX+1 (663970+1), monotonic, no reuse — so every already-minted unit keeps its historical id as a lineage attribute.
  • ⇄ Direct UC write path — writer puts the minted id straight into UC, Hendrix reads back. Rejected as default: inverts today's ownership (GIS loses local id authority) and adds a UC round-trip to the upload critical path. option
D3 · PRE-WORKReplacing the Esri Shapeloader — inventory before removal

The DIV1 round-trip is also the promotion path from an edited SDE polygon to a registered prod unit. The direct-to-Hendrix write must replicate what the Shapeloader did besides mint IDs, or behavior is silently dropped.

  • Projection (NAD83→NAD27 / NADCON). ✅ default: drop NAD27, keep NAD83 if no consumer requires it. ⇄ preserve NAD27 if a dependency is found.
  • Validation / repair / topology. Confirm make-valid / dedup / topology checks and port into the upload path (Shapely make_valid — geom-spark precedent).
  • Promotion / QC gate. Enforce the same Status/StatusCode IN (1–4) gate on direct write that distinguishes an editing polygon from a registered UNIT_POLYGON row.
D5a · HARD — largest blast radiusMessage identity — UWI on a new v4 topic
✅ Recommended: re-key to UWI on dp.pres.landtracunit.v4, run in parallel with v3. Producer publishes UWI-keyed messages to v4 (unit_id = UWI, key = key_base + UWI). The existing v3 topic (daapUnitID-keyed) keeps running; each consumer — DSM, DirectAccess, DIBI, Prism, Elasticsearch, DS9, Hendrix gis_exports — migrates v3→v4 on its own schedule; v3 retired when drained. daapUnitID kept as a stable payload attribute. A versioned topic makes the cutover incremental and reversible — no big-bang, v3 is a live fallback throughout. Cost: two topics + double-publish during transition.
  • ⇄ Keep daapUnitID as the key, UWI source-only — lowest blast radius. daapUnitID (Hendrix-minted) stays the key; UWI is enrichment in the payload only; no consumer forks; D5 preserved. Choose if "new identifier" is satisfied by re-sourcing wells on UWI without changing message identity. The natural fallback if v4 is judged too much infra. option
  • ⇄ Big-bang re-key on v3 — backfill every published unit (≤ 663970) under new UWI keys on the same topic, all consumers re-key at once. Highest risk, least long-term overhead. Not recommended given consumer count. option
  • ⚠ Owed regardless. Do downstream consumers accept UWI-shaped keys, and in what migration order? That inventory is the first task if v4 is ratified.
D2 / D2a · TEAMFreeze-detection signal + tracking scripts

Today daapUnitID is an outcome signal (exists only after a successful ingest) — GIS's freeze-detection tripwire (the LND-8911 stall). Minting in Hendrix at upload time makes it an assignment signal, so the tripwire is lost. A replacement is required.

✅ Recommended. New success indicator = a Kafka-publish confirmation written back to a Hendrix tracking column (per unit: reached v4 / materialized / published). Consolidate wellid-updates + daapID-update into one UC-sourced job that updates the tracking table + backfills wellid/daapid in a single script, carrying the new signal — collapsing the Py2/Py3 overlap.
  • ⇄ Re-source both scripts, keep separate — repoint each DIV1→UC individually, carry the indicator, don't consolidate. Less refactoring. option
  • ⇄ Retire both without replacement — only if daapUnitID-as-assignment is accepted and the signal lives elsewhere. Leaves no GIS-side tracking job. Not recommended. option
  • ⚠ Secondary signal candidate: UC-ingest timestamp. Publish-confirmation preferred because it proves the record reached the actual downstream — what the old signal implicitly meant.
D6 · TEAMCutover, seeding, rollback
✅ Recommended sequence. (1) Seed — snapshot DIV1 tblDaapUnit → Hendrix sequence, next-value = MAX+1. Snapshot-and-flip. (2) Dual-run validation — UC-sourced producer beside DIV1-sourced, diff Kafka output before any cutover (gated on D4 pre-work). (3) Parallel publish — double-publish v3 + v4; consumers migrate independently; retire v3 when drained. (4) Rollback — fall back to DIV1-sourced producer / v3 if UC freshness lags.
  • ⇄ Dual-write DIV1 + Hendrix during transition (instead of snapshot-and-flip) — keeps both id stores consistent while consumers migrate; heavier, but removes flip-day risk. option
  • ⚠ Rollback has an expiry. DIV1 is being retired org-wide, so "repoint to DIV1" has a hard deadline — confirm the window before relying on it.

What stays the same

  • Everything from the Airflow producer rightward is structurally unchanged — DSM, the Prefect flow (Materialize→Prepublish→Verify→Publish→Clean), all 6 publish targets. Their only change is a new topic/key to migrate onto, and only if v4 is ratified.
  • The Hendrix SDE hub (landtrac_unit.sde on v03henpdb01) stays the center of gravity — gains the native daapUnitID sequence + tracking column; the SDE tables themselves are unchanged.
  • DS9 enrichment (well status, entitlement, basin/play) is untouched — the UWI pivot only replaces the DIV1 enrichment.
  • reconcile-post-all remains the step that makes GIS-team versioned edits visible to the producer.
