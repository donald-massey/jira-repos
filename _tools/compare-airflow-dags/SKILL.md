# Compare Airflow DAGs

## Purpose

When a DAG is ported to a new Airflow instance or upgraded, the team legitimately
rewrites import paths, swaps operator modules, and renames kwargs. A raw text diff
buries the one thing that matters — *did any task or behavior get lost?* — under
dozens of cosmetic changes.

This skill answers one question with confidence: **does the new DAG do everything
the old DAG did?** It works by extracting a structured inventory from each file
(tasks, dependency edges, per-task args, DAG config, callable bodies) and reasoning
about the differences, separating expected port adjustments from real regressions.

## Workflow

### 1. Locate the two DAG files

The user usually names them or points at a pair like `old_airflow_dag.py` /
`new_airflow_dag.py`. If only one is given, ask for the other. "Old" = the
source-of-truth original; "new" = the ported/migrated version being verified.

### 2. Extract a structured inventory from each

Run the bundled extractor on both files. It parses statically (AST) — no execution,
no Airflow install, no resolving the DAG's imports — so it works on source from any
Airflow version or instance.

```bash
python <skill-dir>/scripts/extract_dag.py <old_dag.py>
python <skill-dir>/scripts/extract_dag.py <new_dag.py>
```

Each emits JSON: `dag` (dag_id, schedule, catchup, default_args expanded, tags, …),
`tasks` (task_id + operator + every kwarg, verbatim), `edges` (dependency graph),
`functions` (module-level def source, for diffing `python_callable` bodies),
`dicts`, `dynamic` (tasks built in loops — see below), and `warnings`.

**Also read both files yourself.** The extractor is a fast, mechanical inventory,
not a substitute for reading. Read the source to catch what static parsing can't
resolve: TaskFlow data dependencies (`b(a())`), tasks generated by helper functions,
conditional branches, and anything in `warnings`/`dynamic`.

### 3. Diff by structure, not by text

Compare the two inventories along four axes (the four the user cares about):

- **Task inventory** — set-diff the `task_id`s. Every old task_id must exist in new.
  A missing one is the headline regression. Note operator-type changes for the same
  task_id (e.g. `BashOperator` → `KubernetesPodOperator`) — could be an intended
  re-platforming or a behavior change; investigate the args.
- **Dependency graph** — compare `edges` as a set of (upstream, downstream) pairs.
  A dropped edge changes execution order or removes a gate; a fan-out/fan-in that
  collapsed to serial (or vice versa) changes concurrency. Flag both.
- **Per-task config** — for each shared task_id, diff its `args`. Focus on args that
  change *what the task does or its reliability*: `bash_command`, `python_callable`,
  `sql`, `application`/`application_args`, `image`/`cmds`/`arguments`, `trigger_rule`,
  `retries`, `pool`, `conn_id`/`*_conn_id`, `execution_timeout`, `json` (Databricks).
  For each differing `python_callable`, diff the two function bodies from `functions`.
- **DAG-level config** — diff `dag`: `schedule`/`schedule_interval`, `catchup`,
  `max_active_runs`, `default_args` (retries, callbacks, timeouts), `tags`,
  `start_date`. A `catchup` flip or a schedule change alters run behavior materially.

### 4. Classify every difference

This is the heart of the skill. Sort each difference into one of two buckets. When
unsure, put it in "needs review" rather than dismissing it — a false alarm costs a
glance; a missed regression ships broken.

**Expected port adjustment** (cosmetic — note but don't alarm). Common Airflow 1→2 /
instance-migration changes:

| Change | Why it's expected |
|---|---|
| `airflow.operators.bash_operator` → `airflow.operators.bash` | Airflow 2 module rename |
| `airflow.contrib.operators.*` → `airflow.providers.*` | contrib moved to provider packages |
| `schedule_interval=` → `schedule=` | Airflow 2.4+ kwarg rename (same value = no behavior change) |
| removal of `provide_context=True` | Airflow 2 always passes context |
| `PythonOperator` → `@task` (TaskFlow) with same callable | API modernization, same work |
| connection id renamed to match new instance's Connections | new env has different Connection names |
| Variable/pool names re-pointed at the new instance | infra, not logic |

A renamed kwarg with the **same value** is not a regression. A renamed connection id
is only fine if the new instance actually has that connection configured — note it as
an assumption to verify.

**Real regression / behavior change** (this is what the user is hunting):

- A task_id in old with no counterpart in new (dropped task).
- A dependency edge in old absent in new (broken wiring / lost gate).
- Same task_id but a materially different command/callable/sql/image.
- `retries` lowered, `trigger_rule` changed, `execution_timeout` removed, an
  `on_failure_callback`/`on_success_callback` dropped.
- `catchup` flipped, `schedule` changed to a different cadence, `max_active_runs` changed.
- A `python_callable` body that changed in substance (not just comments/formatting).

### 5. Write the report

Write the report to a folder named after the DAG — `<dag_id>/dag_comparison.md`,
relative to where the DAG files live (e.g. the ticket folder). Use the `dag_id`
from the extractor's `dag` output (they share one when it's an old/new pair); if the
two differ, use the new DAG's `dag_id`, and if it can't be resolved statically (e.g.
`dag_id=DAG_NAME`), read the source to find its literal value. Create the folder if
it doesn't exist. This keeps each DAG's report grouped under its own name when several
DAGs are compared in the same workspace. Use this structure exactly — the verdict goes
first so the reader gets the answer immediately:

```markdown
# DAG Comparison: <old file> vs <new file>

## Verdict
<ONE of:>
- ✅ **No functional gaps.** Every task, edge, and behavior in the old DAG is present
  in the new DAG. Differences are all expected port adjustments (listed below).
- ⚠️ **Regressions found.** The new DAG is missing N task(s) / M edge(s) / behavior
  changes (detailed below). These must be resolved before the new DAG replaces the old.
- ❓ **Cannot fully verify statically.** <reason — e.g. dynamic task generation in a
  loop; TaskFlow data dependencies> — manual review of the flagged sections required.

## Regressions & behavior changes
| Severity | Type | Old | New | Impact |
|---|---|---|---|---|
| 🔴 | Dropped task | `notify` (BashOperator) | — | Downstream notification no longer runs |
| 🟡 | Config change | `retries: 3` | `retries: 2` | Fewer retries on failure |
<only real regressions here; empty table => say "None.">

## Expected port adjustments
<bullet list of cosmetic changes, so the reader sees they were considered and dismissed>

## Needs manual verification
<assumptions and un-resolvable items: renamed conn_ids to confirm in the new instance,
dynamic tasks the parser couldn't enumerate, TaskFlow data deps, changed callable bodies>

## Coverage
- Tasks: old N / new M
- Edges: old N / new M
- Dynamic/unresolved: <count + what>
```

Print the verdict line to the terminal too, so the user gets the answer without
opening the file.

## Notes on trust

- **Never claim "no gaps" from the extractor alone if there are `dynamic` entries or
  warnings.** Static parsing cannot enumerate tasks built in loops or by factory
  functions. Say so in the verdict and route those to "Needs manual verification".
- The extractor renders arg values as source strings (e.g. `"'echo start'"`), so a
  quoting/formatting-only difference is not a behavior change — compare meaning, not
  the string byte-for-byte.
- If the two DAGs have different `dag_id`s, confirm with the user they're really the
  old/new pair and not two unrelated DAGs before reporting.
